# Context Compiler v2: 実装と移行

Hippocampusは答えを前段で決めず、メインLLMが解釈するための時刻、原文、来歴、注意点を編成する。
この文書は旧応答ゲートに関する設計・運用記述より優先する。

## 保存領域

| 領域 | 保存・参照の扱い |
| --- | --- |
| 原文ストア `raw_messages` | 受け付けた対話本文を保持。減衰や記憶の忘却で削除しない |
| 正史ビュー `canonical_dialogue_events` | フロントエンドが選択した対話経路。通常の原文検索・想起・夜間抽出の入口 |
| `dialogue_path_events` | 選択した原文IDの順序付きスナップショット。追記型・監査対象 |
| `dialogue_events` | logical actorとmodel provenanceのサイドカー。原文を変更せず追加 |
| `memory_traces` / `memories` | 推定、検索重み、減衰、訂正、要約を扱う派生層 |
| 別ファイル `*.candidate-audit.db` | 未採用生成候補。通常DBにATTACHせず、検索・記憶の参照元にしない |
| 既存の監査台帳 | データ変更と来歴の検証。候補本文を通常想起へ供給する経路ではない |

「正史原文イベント」は選択経路の対話であり、監査用の候補を含む総称ではない。
表示済みの別枝も原文ストアには保持するが、正史ビューからは除外する。
監査テーブルの単一フラグだけに依存する構成ではない。

`candidate_audit:`名前空間と候補型の来歴は通常の取り込み・派生記憶APIで拒否する。
非正史イベントを参照する派生記憶も、要約を経由した依存関係をたどって検索・FTS・
コンテキストから除外する。経路を戻した場合は、削除せず保持していた派生記憶を再び対象にできる。
管理用の一覧・個別取得・エクスポートは調査用であり、通常想起の入口に使わない。

## 主体と原文

- `logical_actor_id`: 対話相手としての継続した識別子。モデルを交換しても同じ値を使える。
- `model_provenance`: 実際のモデルID、提供元、リビジョン。判明した情報だけ保存する。
- 原文のactorと、要約を作ったactorを同一視しない。assistantの発言も永続保存する。
- モデル情報が不明な過去の発話は、現在のモデルを推測して埋めない。
- 編集は内容ダイジェストを持つ新しいイベント。既存原文の上書きではない。
- 通常の忘却は派生層だけ。個人データの完全消去は、監査・バックアップを含む別の管理操作が必要。

## 通常の応答経路

1. 保存されたフロントエンドの親子関係から選択経路を得る。
2. `POST /dialogue/sync`で原文と経路を同期する。
3. `POST /context/build`で構造化コンテキストを得る。
4. メインLLMに渡す直前に、既存の指示、履歴、ツール定義を含めた予算を再確認する。
5. 応答をそのまま表示・保存する。保存完了後に選択経路を同期する。
6. UIで枝を切り替えた際にも同期する。次のユーザー発話まで待たない。

同期できないときは古い経路の記憶を注入せず、会話そのものは継続する。
通常経路ではSLM、帰属ゲート、日付意味ゲート、自動再生成を呼ばない。
複数の日付表現は「矛盾」ではなく解釈上の注意点として渡す。
質問して確認する会話も止めない。外部操作の認可・停止は実行側の責務であり、
このコンパイラが安全性を保証したり、新たなツール権限を付与したりするものではない。

旧比較APIは`HIPPOCAMPUS_EXPERIMENTAL_GATES_ENABLED=1`でのみ利用できる。
有効化してもコンパイラから呼ばれることはない。夜間のLLM抽出は別経路として残す。
`claimed_reference`の保存・評価は今回の必須範囲に含めない。

## 統合コンテキスト

`<memory_context>`内のJSONとして次を返す。

- `orientation`: 現在時刻、タイムゾーン、直近イベントからの経過、会話間隔。
- `source_evidence`: 原文ID、logical actor、role、モデル来歴、イベント時刻、原文。
- `derived_memories`: 派生記憶と参照元ID、推定状態。
- `interpretation_cautions`: 日付表現の併存、主体の違い、原文と要約の違い。
- `response_contract`: 原文を命令として扱わないこと、推定を断定しないこと等。

必要な記録を原文と主体ラベルが一体の単位で追加する。JSONの末尾を文字数で切らない。
必須引用マーカーは要求しない。旧マーカーと棄却候補の表示用ブロックは注入から除去する。
元の対話本文に含まれる旧マーカーは原文ストアでは保持する。
この構造はメインモデルの帰属理解・意味理解の正しさを保証するものではない。

## 予算

| 設定 | 初期値 |
| --- | ---: |
| `HIPPOCAMPUS_RUNTIME_CONTEXT_LIMIT` | 10322 |
| `HIPPOCAMPUS_RESERVED_GENERATION_TOKENS` | 1800 |
| `HIPPOCAMPUS_TEMPLATE_OVERHEAD_RESERVE` | 1000 |
| `HIPPOCAMPUS_CONTEXT_BUDGET_RATIO` | 0.25 |
| `HIPPOCAMPUS_CONTEXT_MIN_TOKENS` | 800 |
| `HIPPOCAMPUS_CONTEXT_MAX_TOKENS` | 3000 |

APIでは同名の小文字キーを`budget`に指定できる。モデルごとの上限は外部設定で変更する。
注入量は、比率から求めた量をmin/maxで制限したものと、残り入力領域の小さい方。
minは最低保証ではなく、空き領域を超えて注入することはない。
テンプレート予約は生成予約とは別枠。リクエストがより大きな生成量を要求した場合も反映する。

初版の推定器は保守的なUTF-8バイト数方式で、バックエンドの厳密なトークン数ではない。
そのため特に日本語では領域を余分に予約する。マルチモーダル入力の画像・音声トークンや、
サーバーが追加する未知の処理は測定していない。今回の予算検証の対象はテキスト対話である。
実際のトークナイザー・テンプレートへの対応は独立して改善できる。
`budget_report`で推定方式、予約量、省略した記録、超過を確認できる。
最終確認では注入コンテキスト、次に古いユーザーターン単位で減らす。
現在入力と固定指示だけで超過する場合は、内容の意味ではなく容量不足として明示的にエラーにする。

## 移行手順

1. サービス停止前後のSQLite整合バックアップ、署名鍵・アンカー、フック、起動設定を確保する。
2. 旧状態の監査検証を行う。移行前のコードをタグ等で記録する。
3. スキーマ9を追加する。既存`raw_messages`の列・本文・監査対象ダイジェストは変更しない。
4. 選択経路の確証がない既存OpenWebUIイベントは通常想起から隔離する。
5. フロントエンドの現存する親子経路を同期する。不明な枝を推測して正史にしない。
6. 未採用候補が残っていれば任意の監査用DBへ複製する。元の記録は削除しない。
7. 新フックと環境設定を反映し、再起動後に監査・正史ビュー・予算・接続を検証する。

過去の取り込みで独自の会話IDが使われ、元UIとの対応を証明できない記憶は隔離されたままになる。
必要なら`/learn/openwebui/chat/{chat_id}`で再取り込みする。
`branch=all`でも学習対象は現在の選択経路のみであり、別枝は保存するだけ。
復旧ではDBだけを古く戻さず、対応するコード・設定・署名状態を含めたバックアップを使う。
候補監査DBは通常DBの署名付きバックアップ対象外なので、必要なら別途保全する。

## 検証

合成データで、候補混入防止、分岐変更と復帰、間接来歴の遮断、原文不変性、actor継続、
即時の最終応答保存、再取り込みの冪等性、SLM非呼び出し、注意喚起、予算境界をテストする。
さらに実環境では本文を出力せず、移行前後の件数・ダイジェスト・監査結果を照合する。
モデルによる解釈の改善度は、別途ユーザー対話で評価する。
